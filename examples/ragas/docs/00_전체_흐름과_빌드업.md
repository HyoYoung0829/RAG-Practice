## 왜 헷갈렸는지 — 두 가지 축이 섞여 있었다

이번 파트에서 나온 개념들은 사실 **서로 다른 두 개의 질문**에 대한 답이 섞여서 나온 거야.

**축 1. "무엇을 평가하냐"** (평가 대상)
- 합성 데이터셋 자체의 품질
- RAG 파이프라인이 낸 답변 하나
- RAG 파이프라인 전체(실험)의 종합 성능
- 실험 A와 실험 B의 상대 비교
- 배포된 서비스의 실시간 트래픽

**축 2. "누가/어떤 도구가 만들었냐"** (소속 생태계)
- RAGAS (RAG 평가 전용 라이브러리)
- LangChain (`langchain.evaluation` — 범용 평가 클래스 모음)
- LangSmith (평가를 실행/기록/비교/운영하는 플랫폼)

이 두 축을 표 하나로 겹쳐보면 전체 그림이 잡혀.

| | RAGAS | LangChain | LangSmith |
|---|---|---|---|
| **역할** | RAG 특화 평가 로직 (질문 생성 + RAG 채점 지표) | 범용 평가 로직 (QA/Criteria 등 채점 클래스) | 평가를 실행·기록·비교·운영하는 **플랫폼** |
| **제공하는 것** | `TestsetGenerator`, `evaluate()` + Faithfulness 등 지표 | `load_evaluator()`로 불러오는 평가 체인들 | `evaluate()`, `summary_evaluators`, `evaluate_comparative()`, 온라인 평가자 |
| **이번 파트에서 위치** | 01번 파일 앞부분 + 05번 파일 | 02, 03번 파일 | 04번 파일 (+ 01, 02, 03의 실행 환경) |

## 전체 빌드업 (왜 이 순서로 배웠는가)

```
[1단계] 시험 문제지 만들기 — 01번 파일
   RAGAS로 합성 데이터셋 생성
   → 근데 이 문제지(질문들) 자체가 괜찮은 퀄리티인지 먼저 점검해야 함
   → "RAGAS로 데이터셋을 평가한다"는 게 바로 이 단계 (RAG 파이프라인이 아직 등장 안 함)

[2단계] 채점 도구/어휘 배우기 — 02, 03번 파일
   "질문-검색문서-답변" 이 세 요소 사이의 관계를 어떻게 채점할지
   → LLM에게 판단시키는 방법 (LLM-as-a-Judge, off-the-shelf 평가자)
   → LLM 없이 통계로 채점하는 방법 (휴리스틱, BLEU 등)
   이 단계에서는 아직 "내 RAG를 채점한다"기보다, "채점 도구 자체가 뭐가 있는지" 배우는 단계

[3단계] 그 채점 도구를 실전 운영에 써먹기 — 04번 파일
   챕터가 "랭스미스 API를 활용한 프롬프트 최적화"로 넘어가면서
   → 2단계에서 배운 채점 도구들을 LangSmith 위에서 실제로 실행
   → 실험끼리 비교하고(Compare, Pairwise), 전체를 집계하고(Summary Evaluator),
     안정성을 확보하고(반복평가), 배포 후에도 계속 돌리는(온라인 평가자) 법을 배움

[4단계] 원점으로 돌아와서 진짜 RAG 파이프라인 채점 — 05번 파일
   1~3단계에서 배운 재료(데이터셋 + 채점 도구 + 운영 노하우)를 다 합쳐서
   → 이번엔 데이터셋이 아니라 "내 RAG 파이프라인의 실제 출력"을 RAGAS로 채점
   → Faithfulness, Context Precision/Recall, Answer Relevancy로 최종 성능 확인
```

**RAGAS가 처음(1단계)과 끝(4단계)에 다시 나오는 이유**: 처음엔 "문제지가 괜찮은가"를 봤고, 끝에선 "그 문제지로 내 RAG가 시험을 잘 봤는가"를 본 거야. 같은 라이브러리, 다른 평가 대상. 이 차이를 05번 파일 첫머리에서 다시 한번 명확히 짚어뒀어.

## 핵심 개념 vs 부가 개념 — 전체 지도

각 파일 안에서도 표시해뒀지만, 전체적으로 "이건 꼭 알아야 하는 개념", "이건 그 개념의 하위 디테일"을 구분하면:

| 레벨 | 개념 |
|---|---|
| **핵심 (독립된 개념)** | 합성 데이터셋, LLM-as-a-Judge, 3가지 평가 관계 축, 휴리스틱 평가, Summary Evaluator, Groundedness, Pairwise 평가, 반복평가, 온라인 평가자, RAGAS 지표(Faithfulness 등) |
| **핵심의 하위 종류 (같은 레벨끼리 나열)** | QA/Context-QA/Criteria/임베딩거리 평가자 (전부 "off-the-shelf 평가자"라는 같은 카테고리 안의 종류들) / BLEU/ROUGE/METEOR/SemScore (전부 "휴리스틱 지표"라는 카테고리 안의 종류들) |
| **부가 디테일 (독립 개념 아님)** | 데이터셋 적정 규모, 데이터셋 원격 관리, Criteria의 세부 기준 목록, n-gram 중첩/정밀도/간결성 패널티(=BLEU 내부 계산 요소) |

## 실무 사용 여부 — 요약

| 도구/개념 | 실무에서 RAG 평가 목적으로 자주 쓰이나 |
|---|---|
| RAGAS (데이터셋 생성 + Faithfulness 등) | **매우 자주 씀** — RAG 평가의 사실상 표준 중 하나 |
| LangChain off-the-shelf 평가자 (QA/Criteria 등) | RAG 평가엔 잘 안 씀. **RAG 아닌 일반 LLM 앱 평가**에 주로 쓰임 |
| 휴리스틱 지표 (BLEU 등) | 단독 주력 지표로는 잘 안 씀. **저비용 1차 필터**로 LLM 평가와 같이 씀 |
| LangSmith 운영 기능 (Compare/Summary/Pairwise/반복/온라인) | **자주 씀** — LangSmith 쓰는 팀이면 평가 운영의 표준 워크플로우 |

각 파일에도 더 자세한 실무 사용 근거를 적어뒀어.
