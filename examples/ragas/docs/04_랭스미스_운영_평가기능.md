# 04. LangSmith 운영/실험관리 평가 기능

> 재료가 된 평가자들: [02_LLM_단일출력_평가자.md](02_LLM_단일출력_평가자.md)

**이 파일의 위치**: 지금까지([02](02_LLM_단일출력_평가자.md), [03](03_휴리스틱_평가지표.md)번 파일)는 **"답변 하나를 어떻게 채점하냐"**였다면, 여기서부터는 **"그 채점을 어떻게 실제로 돌리고, 여러 실행/버전에 걸쳐 운영하냐"**로 관점이 바뀌어. LangSmith가 제공하는 건 새로운 채점 로직이 아니라, **채점을 실행·기록·비교·자동화하는 플랫폼 기능**이야.

## 1. 실험별 비교 분석 (핵심 개념)

여러 실험(예: 프롬프트 버전 A vs B, 모델 A vs B)을 **나란히 놓고 점수를 비교**하는 LangSmith UI 기능(Compare). 새로운 채점 로직이 아니라, **기존 채점 결과를 여러 버전에 걸쳐 놓고 보는 활용법**이야.

---

## 2. Summary Evaluator — 실험 전체 수준 평가 (핵심 개념)

일반 평가자는 **"실행(Run) 하나 = 채점 한 번"**인데, 어떤 지표는 **개별 실행 하나만 봐서는 계산이 안 되고 전체 실험을 다 모아야 계산**돼. 예: "전체 100개 질문 중 몇 %가 관련성 있었나?"

```python
def relevance_score_summary_evaluator(runs: List[Run], examples: List[Example]) -> dict:
    rq_scores = 0
    for run, example in zip(runs, examples):   # 전체 실행을 순회
        ...
    final_score = rq_scores / len(runs)         # 비율로 집계
    return {"key": "relevance_score", "score": final_score}

evaluate(
    my_chain, data=dataset_name,
    summary_evaluators=[relevance_score_summary_evaluator],  # 별도 파라미터
)
```

**주의**: `relevance_score_summary_evaluator` 같은 함수 자체는 LangSmith가 제공하는 게 아니라 **개발자가 직접 짜는 커스텀 코드**야. LangSmith가 주는 건 "이 시그니처(Run 리스트, Example 리스트를 받는 함수)로 짜면 전체 실행 끝나고 자동 호출해준다"는 **실행 규격**뿐.

| | 일반 평가자 | Summary Evaluator |
|---|---|---|
| 입력 | Run 하나, Example 하나 | Run **리스트**, Example **리스트** |
| 결과 확인 단위 | 개별 항목별 | **실험(Experiment) 단위로만** 확인 가능 |

## 3. Groundedness 평가자 — 환각(hallucination) 확인 (핵심 개념)

**답변이 검색된 컨텍스트에 실제로 근거하고 있는가**를 채점. [02번 파일](02_LLM_단일출력_평가자.md)의 **③번 축(Retrieval-Answer)**, 그리고 [05번 파일](05_RAGAS_RAG_파이프라인_평가.md)에 나오는 **Faithfulness와 사실상 동일한 개념**이야. 원리는 이래: 응답의 각 문장마다 컨텍스트에서 근거를 찾고, 있으면 1점 없으면 0점, 평균을 최종 점수로 냄.

교재는 **Upstage GroundednessCheck**를 예제로 씀:

```python
from langchain_upstage import UpstageGroundednessCheck

groundedness_check = UpstageGroundednessCheck()
groundedness_check.invoke({"context": "삼성전자 AI는 빅스비에요", "answer": "삼성전자 AI는 가우스입니다"})
# -> "notGrounded" (컨텍스트에 없는 내용)
```

**왜 하필 Upstage냐**: RAGAS의 Faithfulness나 다른 유사 도구는 대부분 영어 기준 프롬프트/모델이라, 한국어 문서에는 성능이 떨어질 수 있어. Upstage는 한국 기업이 **한국어 특화로 튜닝한 전용 판정 모델**이라 한국어 RAG 평가에 더 안정적.

### 대표적인 그라운디드니스 제공 도구들

| 도구 | 방식 | 특징 |
|---|---|---|
| **Upstage GroundednessCheck** | 전용 파인튜닝 모델 | 한국어 특화 |
| RAGAS Faithfulness | 범용 LLM 프롬프트 판단 | RAGAS 파이프라인과 통합 ([05번 파일](05_RAGAS_RAG_파이프라인_평가.md)) |
| TruLens Groundedness | LLM feedback function | 청크 단위 근거 추적 |
| Guardrails AI Hallucination Validator | 파인튜닝 모델 | 사후 평가 아닌 실시간 차단(guardrail)에도 씀 |

## 4. Pairwise 평가 — 두 실험 맞대결 (핵심 개념)

일반 평가자는 **"답변 하나에 점수 하나"**인데, Pairwise는 **"두 실험의 답변을 나란히 놓고 어느 게 더 나은지"** 직접 비교해.

```python
def pairwise_evaluator(inputs: dict, outputs: list[dict], reference_outputs: dict) -> dict:
    # outputs는 실험 A와 B 결과가 담긴 2개짜리 리스트
    ...

from langsmith.evaluation import evaluate_comparative
evaluate_comparative(["experiment-A", "experiment-B"], evaluators=[pairwise_evaluator])
```

절대 점수(0.72 vs 0.68)로 비교하기 애매한 주관적 기준(자연스러움, 선호도 등)을 비교할 때 특히 유용해.

---

## 5. 반복 평가 (핵심 개념)

LLM은 같은 입력에도 매번 답변이 살짝 다를 수 있어(비결정성). **한 번만 평가하면 그 점수가 "진짜 실력"인지 "그날의 운"인지 구분이 안 돼.**

```python
evaluate(
    my_chain, data=dataset_name, evaluators=[...],
    num_repetitions=3,  # 같은 데이터셋을 3번 반복 실행 + 채점
)
```

여러 번 반복해서 **평균과 편차**를 같이 보면, 점수가 안정적인지(편차 작음) 불안정한지(편차 큼) 같이 확인할 수 있어.

---

## 6. 온라인 평가자 (핵심 개념 — 성격이 가장 다름)

지금까지는 전부 **오프라인 평가**(개발 단계에서, 준비된 데이터셋으로, 수동 실행)였는데, 온라인 평가자는 **배포된 서비스의 실시간 사용자 트래픽을 자동으로 채점**하는 거야.

| | 오프라인 평가 (위 1~5번) | 온라인 평가자 |
|---|---|---|
| 시점 | 개발 중, 수동 실행 | 배포 후, 실시간 자동 |
| 데이터 | 준비된 테스트셋 | 실제 사용자의 진짜 질문 |
| 목적 | 출시 전 검증 | 운영 중 모니터링 |

두 종류가 있음:
- **LLM-as-a-Judge**: 독성/환각/정확성 등을 실시간 트래픽에 자동 적용
- **Custom Code**: LLM 호출 없이 파이썬/JS로 직접 짠 검증 로직 (JSON 유효성 등)

**자동화 규칙(Automation Rule)**으로 설정: 트레이싱 프로젝트에 규칙을 걸어두면, 조건에 맞는 트레이스마다 자동으로 채점됨. 평가 대상이 된 트레이스는 자동으로 더 긴 보관 기간으로 업그레이드됨(비용에 영향 있음).

## 실무 사용 여부

| 항목 | 실무 사용 |
|---|---|
| 실험 비교(Compare) | **자주 씀** — 프롬프트/모델 버전 비교의 기본 워크플로우 |
| Summary Evaluator | 자주 씀 — 집계 지표가 필요한 경우 표준적 방법 |
| Groundedness 평가자 | **매우 자주 씀** — 환각 탐지는 RAG 운영의 핵심 관심사 |
| Pairwise 평가 | 씀 — 특히 주관적 품질 비교, A/B 테스트 상황 |
| 반복 평가 | 자주 씀 — 신뢰도 있는 결과를 보고할 때 필수적으로 고려됨 |
| 온라인 평가자 | LangSmith로 실제 프로덕션을 운영하는 팀에서 표준적으로 씀. **해커톤처럼 배포 트래픽이 없는 상황에서는 잘 안 씀**(다만 "운영까지 고려한 설계"라는 어필 포인트로는 유효) |

전반적으로 **이 파일의 기능들은 LangSmith를 이미 쓰고 있는 팀이라면 평가를 운영하는 표준 방식**으로 자리잡은 편이야.
