# 08. 튜닝 보고서 (계속 업데이트)

> 전체 지도: [00_전체_흐름과_빌드업.md](00_전체_흐름과_빌드업.md)
> Before/After(리랭커) 리포트: [07_리랭커_적용_평가_결과.md](07_리랭커_적용_평가_결과.md)

[06](06_베이스라인_평가_결과.md)·[07](07_리랭커_적용_평가_결과.md)번 리포트로 나이브 RAG와 리랭커 적용 결과를 기록했다. 이제부터는 그 결과에서 드러난 약점을 하나씩 실험으로 검증하며 튜닝한 기록을 이 문서에 계속 추가한다.

**코드 구조**: 기존 `main.py`/`rag_pipeline.py`는 06·07번 결과를 재현하는 기록용으로 그대로 둔다. 튜닝 실험은 `main_tuned.py`/`rag_pipeline_tuned.py`에서 진행하고, 바뀐 파라미터만 새로 정의하고 나머지는 `rag_pipeline.py`의 함수를 그대로 재사용한다.

**노이즈 판단 기준** (이 문서 전체에서 적용):
- 0.01~0.05 차이: 노이즈로 취급, 무시
- 0.1~0.3 차이: 애매함 — 여러 번 재현되는지 확인 필요
- 0.3 이상 또는 0↔1 반전: 실제 신호일 가능성 높음 (단, 사실 주장이 0개인 답변 같은 경계 케이스는 예외적으로 크게 흔들릴 수 있어 항상 실제 답변/문맥을 같이 확인)

## 실험 1: 청크 크기 축소 (`chunk_size` 800 → 300)

### 가설

[07번 리포트](07_리랭커_적용_평가_결과.md)에서 질문 0("AI 로보틱스 시장 2030년 전망")이 리랭커로도 해결되지 않았던 이유는, 정답 문장("643억 달러")이 담긴 청크가 800자 안에 서로 다른 3개 소주제(트렌드 서두/시장 통계/정책 투자)를 함께 담고 있어 임베딩이 희석됐기 때문이었다(전체 106개 청크 중 유사도 23등). 청크를 문서의 불릿(`●`) 하나 정도 크기로 줄이면 주제가 안 섞여 순위가 오를 것이라는 가설.

### 변경 사항

| 항목 | Before (`rag_pipeline.py`) | After (`rag_pipeline_tuned.py`) |
|---|---|---|
| `chunk_size` | 800 | 300 |
| `chunk_overlap` | 100 | 50 |
| 그 외 전부 (k=4, 리랭커 fetch_k=8/top_n=4, 임베딩·LLM 모델, 프롬프트) | 동일 | 동일 |

청크 개수: 106개 → **250개**

### 검증: 정답 청크 순위

```
Before: 106개 중 23등 (score=1.2065)
After : 250개 중  1등 (score=0.8623)
```
청크를 쪼개자 "643억 달러" 문장이 독립된 청크로 분리되며 유사도 순위가 극적으로 상승 — 가설이 직접 확인됨.

### 결과 (RAGAS 평가, 질문 5개 평균)

| 지표 | 베이스라인 (chunk=800) | 튜닝 베이스라인 (chunk=300) | 리랭커 (chunk=800) | 튜닝 리랭커 (chunk=300) |
|---|---:|---:|---:|---:|
| Faithfulness | 0.80~1.00* | 0.83 | 0.80~1.00* | 0.90 |
| Answer Relevancy | 0.49 | **0.84** | 0.67 | **0.85** |
| Context Precision | 0.70 | **0.97** | 0.80 | **1.00** |
| Context Recall | 0.40 | **1.00** | 0.80 | **1.00** |

\* 채점 노이즈로 실행마다 값이 흔들림 ([07번 리포트](07_리랭커_적용_평가_결과.md) "채점 자체의 노이즈" 참고)

### 해석

- **Context Recall이 베이스라인만으로도 1.00 달성** — 청킹만 고쳐도 리랭커 없이 검색 실패 문제가 거의 해소됨. 리랭커의 역할은 "누락된 걸 찾아주는 것"에서 "이미 찾은 걸 조금 더 다듬는 것"으로 축소됨.
- **Answer Relevancy도 큰 폭 개선(0.49→0.84)** — 검색이 정확해지니 "모른다"는 회피성 답변이 줄고 질문에 부합하는 답이 늘어난 간접 효과.
- **Faithfulness는 일부 질문(질문 2: 0.67, 질문 4: 0.5)에서 오히려 하락** — 원인 미확정. 청크가 작아지며 답변에 필요한 문맥이 여러 청크로 쪼개져, LLM이 인접 청크 밖의 내용을 살짝 섞어 답했을 가능성(사전 예상했던 "너무 작으면 문맥 부족" 트레이드오프)과, 단순 채점 노이즈일 가능성 둘 다 남아있음 — **다음 확인 필요 항목**.

### 다음 확인 필요 항목

- [ ] 질문 2·4의 Faithfulness 하락이 노이즈인지 실제 문맥 부족 문제인지, 답변·문맥 직접 대조로 검증
- [ ] `chunk_overlap`을 더 키워서(예: 100) 청크가 작아지며 생긴 문맥 단절을 보완할 수 있는지 실험

## 실험 2: RAGAS 채점 노이즈 원인 규명 (temperature 고정 + 프롬프트 수정)

실험 1에서 남긴 "질문 4의 Faithfulness가 왜 낮은가"를 추적한 기록. 결과적으로 노이즈가 아니라 **우리 코드의 실제 버그**였다.

### 2-1. `temperature=0` 고정으로 노이즈와 신호 분리

`evaluate()`에 `llm`을 안 넘기면 RAGAS가 내부적으로 만드는 기본 채점 LLM(`ChatOpenAI(model="gpt-4o-mini")`)에 `temperature`가 지정돼 있지 않아, 채점 자체가 매번 흔들릴 수 있음(질문 0·2 확인). `main_tuned.py`에 `JUDGE_LLM = LangchainLLMWrapper(ChatOpenAI(model="gpt-4o-mini", temperature=0))`를 추가하고 `evaluate(..., llm=JUDGE_LLM)`으로 고정.

**효과 확인**: 온도 고정 전/후로 실험 1을 3번 반복 실행한 결과, 질문 0·2는 실행마다 값이 계속 바뀌어 노이즈로 확정. 반면 **질문 4는 0.5로 세 번 모두 정확히 재현**돼 "진짜 문제"로 판명 — temperature 고정이 노이즈와 신호를 구분하는 데 실제로 도움이 됨(단, 완전한 결정론은 아님).

### 2-2. 질문 4의 Faithfulness=0.5 원인: LLM이 본 문맥 ≠ RAGAS가 채점한 문맥

`rag_pipeline.py`의 `ask()`를 보면:
- LLM에게 주는 문맥: `f"[페이지 {doc.metadata['page']}]\n{doc.page_content}"` (페이지 번호 포함)
- RAGAS에 넘기는 `contexts`: `[doc.page_content for doc in docs]` (페이지 번호 **없음**)

프롬프트가 "답변 마지막에 (출처: N페이지)를 표시하라"고 요구해서, 답변엔 "(출처: 2페이지)"가 붙는데, RAGAS Faithfulness가 그 주장을 검증하려 해도 넘겨받은 `contexts`엔 "2페이지"라는 텍스트 자체가 없다. 답변의 주장을 (1)"350% 성장했다"(문맥에 있음, 지지됨) (2)"출처가 2페이지다"(문맥에 없음, 지지 안 됨) 둘로 쪼개면 정확히 **1/2 = 0.5**가 나오는 것과 일치.

**해결**: 페이지 인용 요구를 프롬프트에서 제거 (`prompt/rag-answer-tuned.yaml` 신규 작성, 기존 `prompt/rag-answer.yaml`은 06·07 리포트 재현을 위해 그대로 둠). `rag_pipeline_tuned.py`에 `build_pipeline()`을 새로 정의해 이 프롬프트를 쓰고, LLM에게 주는 문맥과 RAGAS용 `contexts`를 동일하게(페이지 번호 없이) 맞춤.

### 결과

| 지표 | 실험 1 (인용 있음) | 실험 2 (인용 뺌 + 온도 고정) |
|---|---:|---:|
| 질문 4 Faithfulness (베이스라인) | 0.50 (3회 재현) | **1.00** |
| 질문 4 Faithfulness (리랭커) | 0.50 | **1.00** |
| Faithfulness 평균 (베이스라인) | 0.83 | 0.84 |
| Faithfulness 평균 (리랭커) | 0.90 | 0.84 |
| Context Precision/Recall | 0.97 / 1.00 | 변화 없음 (인용과 무관한 지표라 예상대로) |

### 교훈

**RAG 파이프라인에서 LLM에게 주는 입력과, 평가 프레임워크에 넘기는 "같은" 데이터가 실제로 일치하는지 반드시 확인해야 한다.** 겉보기엔 사소한 포맷 차이(페이지 번호 유무)가 평가 지표를 실제 품질과 무관하게 흔들 수 있다.

### 새로 발견된 항목 (다음에 파볼 것)

- [x] 질문 2("유형 분류")의 Faithfulness가 베이스라인·리랭커 둘 다 0.2로 낮게 나온 원인 → **아래 실험 3에서 규명 완료 (우리 쪽 문제 아님)**
- [x] `chunk_overlap` 확대 실험 (실험 1에서 이월) → **아래 실험 4에서 진행**

## 실험 3: 채점 LLM 자체의 오판 사례 (질문 2)

실험 2에서 새로 발견된 "질문 2 Faithfulness=0.2"를 Q4와 같은 방식(답변·문맥 직접 대조)으로 검증.

### 대조 결과

```
답변    : "휴머노이드형, 자율주행차형, 드론형, AGV & AMR형 4가지로 구분됩니다."
문맥[0] : "...피지컬 AI를 휴머노이드형, 자율주행차형, 드론형, AGV & AMR형 4가지로 구분하고..."
```

답변이 문맥 문장을 거의 그대로 인용했다. 페이지 인용 같은 부가 주장도 없고(실험 2에서 이미 제거), 질문에 정확히 부합하는 흠잡을 데 없는 답변인데도 Faithfulness가 0.2로 나옴.

### 결론

**Q4와는 성격이 다른 문제.** Q4는 "우리가 RAGAS에 잘못된 데이터(페이지 정보 누락)를 줘서 채점관이 정당하게 감점한" 케이스였다면, 이번은 **"데이터도 맞고 답변도 명백히 옳은데 채점 LLM이 그냥 틀리게 판정한"** 케이스다. 우리 파이프라인 코드로 고칠 수 있는 부분이 아니라, **LLM-as-a-Judge 방식 자체의 한계**로 봐야 한다.

### 교훈

RAGAS 점수가 낮게 나왔다고 무조건 파이프라인 문제로 단정하면 안 된다. 이번 세션에서 확인한 "낮은 점수"의 원인은 세 갈래였다:
1. 실제 파이프라인 결함 (실험 1의 청킹 문제 — 검색 실패)
2. 우리 코드의 버그 (실험 2의 페이지 인용 불일치)
3. 채점기 자체의 오판 (이번 사례 — 재실행하거나 다른 채점 LLM을 써야 개선 여지가 있음, 파이프라인 수정으로는 해결 불가)

**실무적 함의**: 소규모 평가셋에서 이상치 하나를 보면, 파이프라인부터 뜯어고치기 전에 반드시 "① 문맥에 근거가 실제로 있는가 → ② 우리가 채점기에 넘긴 데이터가 LLM이 본 것과 같은가 → ③ 그래도 이상하면 채점기 자체의 한계"의 순서로 원인을 좁혀가는 게 맞다.

## 실험 4: `chunk_overlap` 확대 (50 → 100)

### 변경 사항

`chunk_size=300`은 유지, `chunk_overlap`만 50→100. 청크 개수: 250개 → 296개.

### 결과

| 지표 (평균) | overlap=50 | overlap=100 |
|---|---:|---:|
| Faithfulness (베이스라인) | 0.84 | **1.00** |
| Faithfulness (리랭커) | 0.84 | 0.91 |
| Context Precision | 0.97~1.00 | 1.00 |
| Context Recall (베이스라인) | 1.00 | **0.80** (질문 1에서 0.0으로 하락) |

### 이상치 검증: 질문 1 Context Recall 0.0

```
답변    : "센서, 액추에이터, AI 알고리즘이 통합된 시스템으로 정의됩니다."
문맥[1] : "Yingbo Li(2021) • 센서·액추에이터·AI 알고리즘이 통합된 시스템으로,
          물리적 세계에서 자율적으로 작동하는 지능형 시스템"
```

답변이 문맥을 정확히 인용했다 — 근데 이 문서에는 "피지컬 AI"를 정의한 학자·기관이 여럿(Miriyev & Kovač, **Yingbo Li**, WEF 등)이라 서로 다른 정의가 병렬로 존재한다. 우리 `ground_truth`는 WEF의 "두뇌/감각/연결/행동" 4요소 정의로 고정해뒀는데, 오버랩 확대로 청크 경계가 바뀌면서 검색이 **Yingbo Li의 다른(하지만 똑같이 유효한) 정의**를 상위로 가져왔다. 리트리버도, 답변도 잘못이 없는데 우리가 정답을 하나로만 고정해서 억울하게 감점된 것.

### 결론: 낮은 점수의 4번째 원인 유형

실험 3에서 정리한 3가지(파이프라인 결함 / 우리 코드 버그 / 채점기 오판)에 이어 **4번째 유형**을 확인:

> **4. 평가셋(ground_truth) 자체의 모호성** — 문서에 정답이 여러 개 존재할 수 있는 질문인데 `reference`를 하나로 고정해서, 리트리버·LLM이 "다른 맞는 답"을 냈을 때 부당하게 감점되는 경우. 파이프라인이 아니라 **평가셋 설계 문제**이므로, 질문을 더 구체적으로("WEF가 제시한 정의 기준으로") 바꾸거나 `reference`에 복수 정답을 허용하는 방식으로 고쳐야 함 — 튜닝으로는 해결 불가.

Faithfulness는 오버랩 확대로 개선됐지만(0.84→1.00/0.91), 이게 "문맥 단절 해소" 덕분인지 이번에도 채점 노이즈인지는 추가 반복 실행 없이는 확정할 수 없음 — 이 세션에서는 여기까지만 기록.

## 종합 정리 (이번 튜닝 세션)

| 실험 | 변경 | 핵심 효과 |
|---|---|---|
| 1. 청크 크기 800→300 | 청킹만 변경 | Context Recall 0.40→1.00 (검색 실패 근본 해결) |
| 2. temperature 고정 + 프롬프트에서 페이지 인용 제거 | 채점 인프라 + 프롬프트 | 노이즈/신호 분리, 질문 4의 "가짜 결함"(코드 버그) 제거 |
| 3. 질문 2 Faithfulness=0.2 원인 규명 | (코드 변경 없음, 조사) | 채점기 자체 오판임을 확인 — 손댈 곳 아님 |
| 4. `chunk_overlap` 50→100 | 오버랩만 변경 | Faithfulness 개선, 대신 평가셋 모호성 문제 새로 드러남 |
