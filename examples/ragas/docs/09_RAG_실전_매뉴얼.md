## 한눈에 보는 체크리스트

새 RAG 프로젝트를 시작할 때 순서대로 점검할 것:

- [ ] 문서 로더가 실제로 설치돼 있는 패키지에 의존하는가 (`pypdf` vs `pdfplumber` 같은 함정)
- [ ] 청크 하나가 서로 다른 소주제를 섞고 있지 않은가 (문서 구조를 실제로 눈으로 본 뒤 `chunk_size` 결정)
- [ ] 리트리버가 못 찾는 질문이 있다면, "순위가 낮아서"인지 "애초에 후보 풀 밖"인지부터 구분
- [ ] 리랭커는 후보를 다시 정렬할 뿐, 후보 풀 자체를 넓혀주지 않는다는 걸 기억
- [ ] RAGAS `evaluate()`에 `llm`을 명시했는가 (안 하면 temperature 고정 안 됨)
- [ ] 파이프라인이 LLM에게 준 문맥과, 평가 프레임워크에 넘기는 `contexts`가 **글자 그대로 같은지** 확인
- [ ] 낮은 점수가 나오면 파이프라인부터 고치지 말고 아래 "진단 순서"부터 거칠 것
- [ ] 평가 질문의 정답이 문서 안에서 유일한지, 여러 개 존재할 수 있는 질문은 아닌지 확인

## 1. 파이프라인 구축 단계별 함정

### 문서 로드
- **의존성 함정**: `PyPDFLoader`처럼 흔히 예시에 나오는 로더가 실제 프로젝트엔 설치 안 돼 있을 수 있다(`pypdf` 없음). 프로젝트에 이미 설치된 라이브러리(`pdfplumber`)로 로더를 바꿔 새 의존성 추가를 피할 수 있는지 먼저 확인.
- **단위 확인**: 로더가 페이지 단위로 `Document`를 쪼개는지, 문서 전체를 하나로 주는지부터 확인하고 시작. 이게 이후 청킹·메타데이터 설계를 결정한다.

### 청킹
- **가장 큰 지렛대**: 이번 실습에서 검색 실패의 근본 원인은 임베딩 모델도 리랭커도 아니라 **`chunk_size`가 너무 커서 한 청크에 여러 소주제가 섞인 것**이었다(800자 청크 하나에 "트렌드 서두 + 시장 통계 + 정책 투자" 3개가 혼재). 검색이 이상하면 리랭커나 임베딩 모델부터 바꾸지 말고 **문제의 청크를 직접 열어서 몇 개 주제가 섞여 있는지부터 눈으로 확인**할 것.
- **작게 쪼갤 때의 대가**: 청크를 줄이면 검색 정확도는 오르지만(이번엔 정답 청크 순위가 23등→1등), 문맥이 여러 조각으로 나뉘어 답변이 근거를 온전히 못 담을 수도 있다는 게 이론상 트레이드오프다. (이번 실습에서 실제로 관측된 Faithfulness 하락은 대부분 이 트레이드오프가 아니라 다른 원인(아래 4번 참고)이었지만, 가능성 자체는 항상 열어둘 것.)
- **페이지 단위 분할의 대가**: 페이지(Document) 단위로 각각 쪼개면 출처(페이지 번호) 추적은 되지만, `chunk_overlap`이 페이지 경계를 못 넘어서 그 경계에 걸친 문장은 겹침 없이 끊긴다.

### 검색기 (Retriever)
- **거리 점수 읽는 법**: FAISS 기본은 L2 거리라 **작을수록 유사**. 코사인 유사도(클수록 좋음)와 헷갈리지 말 것.
- **순위 vs 존재 여부**: 검색이 실패했을 때 "몇 등인지"부터 확인해야 한다. 후보 풀(`k`) 안에도 없다면 검색 알고리즘을 아무리 정교하게 바꿔도(리랭커 포함) 소용없다 — 이 경우는 `k`를 늘리거나 청킹을 고쳐야 하는 문제다.

### 리랭커
- **역할의 한계**: 리랭커는 "이미 뽑힌 후보들의 순서를 다시 매기는" 역할만 한다. 정답이 애초에 후보 풀(`fetch_k`)에 없으면 리랭커가 아무리 똑똑해도 꺼내올 수 없다. "리랭커를 붙였는데도 안 된다"는 리랭커가 나빠서가 아니라 **후보 풀이 좁아서**일 수 있다.
- **개선 메커니즘이 두 가지**: (a) 후보 풀을 넓혀서(`fetch_k` ↑) 원래 못 찾던 걸 찾아주는 경우, (b) 이미 후보에 있던 것들 중 우선순위를 정리해서 LLM이 더 적절한 근거를 골라 쓰게 유도하는 경우. 결과가 좋아져도 "왜" 좋아졌는지는 실제 문맥을 열어봐야 구분된다.

## 2. RAGAS로 평가할 때 낮은 점수의 4가지 원인

이번 실습에서 "왜 점수가 낮지?"를 실제로 파봤을 때 매번 원인이 달랐다. **점수가 낮다고 바로 파이프라인부터 고치지 말고, 아래 순서로 원인을 좁혀갈 것:**

| # | 원인 | 확인 방법 | 대응 |
|---|---|---|---|
| 1 | **실제 파이프라인 결함** | 정답 근거가 `retrieved_contexts`에 실제로 있는지 확인 | 청킹/검색 파라미터 튜닝 |
| 2 | **우리 코드의 버그** | LLM에게 준 프롬프트/문맥과, RAGAS에 넘긴 `contexts`가 글자 그대로 같은지 확인 | 코드 수정 (예: 페이지 번호처럼 한쪽에만 있는 정보 제거) |
| 3 | **채점기(LLM-as-a-Judge) 자체의 오판** | 답변이 문맥을 명백히·정확히 인용했는데도 점수가 낮다면 이거 | 파이프라인 문제 아님, 채점 LLM 교체나 반복 실행으로만 완화 가능 |
| 4 | **평가셋(ground_truth) 자체의 모호성** | 문서 안에 그 질문에 대한 답이 여러 개(다른 학자·기관 정의 등) 존재하는지 확인 | 질문을 더 구체적으로 쓰거나, 정답을 복수로 허용 |

**실제 사례**: 1번은 청크 800자 안에 정답이 묻혀 순위 23등으로 밀린 것, 2번은 프롬프트가 요구한 페이지 인용이 RAGAS `contexts`엔 없어서 검증 불가 처리된 것, 3번은 문맥을 그대로 인용한 답변인데도 Faithfulness 0.2가 나온 것, 4번은 "피지컬 AI 정의"에 여러 학자의 서로 다른 정의가 있는데 정답을 하나로만 고정해서 다른 맞는 답이 감점된 것.

## 3. RAGAS 채점 자체를 다룰 때 알아야 할 것

- **온도(temperature) 기본값 함정**: `evaluate()`에 `llm`을 안 넘기면 RAGAS가 내부적으로 만드는 채점 LLM에 `temperature`가 지정돼 있지 않아 채점 자체가 실행마다 흔들릴 수 있다. `LangchainLLMWrapper(ChatOpenAI(model=..., temperature=0))`를 `llm=`으로 명시해서 고정할 것. (단, OpenAI API는 `temperature=0`이어도 100% 결정론은 아니라는 것도 감안.)
- **노이즈 판단 기준** (이번 실습에서 쓴 경험칙):
  - 0.01~0.05 차이: 노이즈, 무시
  - 0.1~0.3 차이: 애매함, 여러 번 재현되는지 확인
  - 0.3 이상 또는 0↔1 반전: 실제 신호일 가능성 높음 (단, "사실 주장이 0개인 답변"처럼 경계 케이스는 예외적으로 크게 흔들릴 수 있음)
- **TestsetGenerator 자동 생성은 실패할 수 있다**: 문서 규모가 작으면(이번엔 49페이지) 멀티홉 질문에 필요한 노드 간 관계가 기본 임계값을 못 넘겨 시나리오가 조용히 0개로 실패할 수 있다(에러 없이 빈 데이터셋 반환, 10분 소요). 소규모 문서에선 처음부터 수기 평가셋도 현실적인 선택지.
- **소규모 평가셋의 한계**: 질문 5개 정도로는 "이게 진짜 개선인지 우연인지" 확신하기 어렵다. 결론을 내리기 전엔 가능하면 실제 답변·문맥을 직접 대조해서 검증할 것 — 숫자만 보고 판단하지 말 것.

## 4. 한 문장 요약

**"점수가 이상하면 코드를 고치기 전에, 실제 문맥과 답변을 먼저 읽어라."** 이번 실습에서 나온 모든 발견은 예외 없이 RAGAS 점수 자체가 아니라 그 뒤에 있는 실제 텍스트를 직접 대조해서 나온 것이었다.
