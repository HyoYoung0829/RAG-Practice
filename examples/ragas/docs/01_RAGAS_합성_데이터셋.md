# 01. RAGAS와 합성 테스트 데이터셋

> 전체 지도: [00_전체_흐름과_빌드업.md](00_전체_흐름과_빌드업.md)

**이 파일에서 다루는 것의 위치**: 아직 "내 RAG 파이프라인을 채점"하는 단계가 아니야. 그 전 단계 — **"채점에 쓸 시험 문제지(데이터셋) 자체를 만들고, 그 문제지 퀄리티를 점검"**하는 단계야.

---

## RAGAS가 뭔지 (핵심 개념)

**R**etrieval **A**ugmented **G**eneration **As**sessment의 약자. RAG 평가 전용으로 만들어진 오픈소스 파이썬 라이브러리(`pip install ragas`)야. "RAG 평가"라는 문제 영역 자체가 아니라, 그 문제를 푸는 **구체적인 도구**를 가리키는 이름.

RAGAS는 크게 두 기능을 갖고 있어:

| 기능 | 모듈 | 이 파일에서 다루는 것 |
|---|---|---|
| 합성 테스트 데이터셋 생성 | `ragas.testset` | ✅ 여기 |
| RAG 파이프라인 채점 | `ragas.metrics`, `evaluate()` | [05번 파일](05_RAGAS_RAG_파이프라인_평가.md)에서 |

## 합성 테스트 데이터셋이란 (핵심 개념)

RAG 파이프라인을 평가하려면 **"질문 - 정답 컨텍스트 - 정답"** 세트가 대량으로 필요해. 이걸 사람이 문서 읽어가며 손으로 만들면 시간이 너무 오래 걸리고, 품질도 사람마다 들쭉날쭉해질 수 있어.

**합성 테스트 데이터셋**은 이 문제를 풀려고, 사람 대신 **LLM에게 원본 문서를 주고 질문-정답 컨텍스트-정답 조합을 자동으로 만들게 하는** 거야.

```python
from ragas.testset import TestsetGenerator

generator = TestsetGenerator.from_langchain(generator_llm, critic_llm, embeddings)
testset = generator.generate_with_langchain_docs(documents, test_size=10)
```

단순히 "이 문단 요약해서 질문 만들어" 수준이 아니라, RAGAS는 난이도/유형이 다양한 질문(간단한 질문, 추론이 필요한 질문, 여러 문서를 넘나드는 질문 등)을 의도적으로 섞어서 생성해. Evol-Instruct라는 기법에서 영감을 받은 진화적 생성 방식을 쓴다고 알려져 있어.

각 샘플은 보통 이 세 가지로 구성돼:

| 구성요소 | 의미 |
|---|---|
| Question | LLM이 문서를 보고 만든 질문 |
| Context | 그 질문에 답하기 위해 참조된 원본 문서 조각 |
| Ground Truth (Answer) | 그 컨텍스트를 바탕으로 한 정답 |

## LangchainLLMWrapper (부가 디테일)

```python
from ragas.llms import LangchainLLMWrapper
generator_llm = LangchainLLMWrapper(ChatOpenAI(model="gpt-4o-mini"))
```

RAGAS는 LangChain 전용 라이브러리가 아니라서, LangChain의 `ChatOpenAI` 같은 모델 객체를 RAGAS 내부가 이해하는 인터페이스로 변환해주는 **어댑터**야. 콘센트 모양 변환 플러그와 같은 역할 — 독립된 개념이라기보다는 "RAGAS가 LangChain 모델을 빌려 쓰기 위한 연결 부품" 정도로 이해하면 충분해.

## 데이터셋의 적정 규모 (부가 디테일)

딱 정해진 "정답 숫자"는 없고, 트레이드오프의 문제야:

- **너무 적으면**: 우연히 잘/못 나온 결과인지 판단하기 어려움 (통계적 신뢰도 낮음)
- **너무 많으면**: LLM 생성 비용이 커지고, 평가할 때도 LLM 채점 비용이 그만큼 커짐

실무/학습에서는 보통 **소규모(수십 개)로 시작해서 파이프라인이 잘 도는지 확인한 뒤, 필요하면 규모를 늘리는 방식**을 많이 써. "이 정도면 충분하다"는 절대 기준보다는, 질문 유형(난이도)이 골고루 커버됐는지가 규모보다 더 중요하게 다뤄지는 경우가 많아.

## RAGAS로 "데이터셋 자체"를 평가하기 (핵심 개념 — 헷갈리기 쉬운 부분)

여기가 가장 헷갈렸을 지점이라 짚고 넘어갈게. **이 단계에서 채점하는 대상은 "내 RAG 시스템의 답변"이 아니라, "LLM이 방금 자동으로 만들어낸 질문-정답 세트 자체"**야.

```
문서 → [LLM] → 합성 데이터셋 생성 (질문 + 정답 컨텍스트 + 정답)
                    ↓
              이 질문들이 실제로 "말이 되는 질문"인가?
              정답이 컨텍스트에서 제대로 도출됐는가?
                    ↓
              품질 낮은 샘플은 걸러내거나 재생성
```

왜 이런 단계가 필요하냐면, LLM이 질문을 자동 생성하다 보면 가끔 **모호하거나, 컨텍스트만으로는 답할 수 없거나, 질문 자체가 어색한 샘플**이 섞여 나올 수 있어. 이런 불량 샘플이 낀 채로 나중에 "내 RAG가 몇 점이다"라고 평가하면, 애초에 시험 문제 자체가 잘못돼서 점수가 왜곡될 수 있어. 그래서 **본 게임(RAG 파이프라인 평가) 전에, 시험 문제지 자체의 퀄리티를 먼저 검수하는 단계**가 들어가는 거야.

> **[05번 파일](05_RAGAS_RAG_파이프라인_평가.md)과의 결정적 차이**: 여기서는 "질문이 좋은 질문인가"를 본다면, 05번에서는 "내 RAG가 이 질문에 잘 답했는가"를 봐. 채점 로직(LLM-as-a-Judge)은 비슷하게 재사용되지만, **채점 대상이 완전히 다름**.

## 데이터셋 원격 관리 (부가 디테일 — 비중 낮음)

만든 합성 데이터셋을 로컬에만 두지 않고 원격 저장소(허깅페이스 데이터셋 허브 등)에 업로드/버전관리하는 방법을 다루는 부분이야. 개념적으로는 **깃허브에 코드를 올리는 것과 똑같은 발상** — "만든 데이터셋을 팀과 공유하고, 버전을 추적하고 싶다"는 실무적 필요를 충족하는 기능이야.

RAG 평가의 **핵심 개념 흐름과는 무관**하니, 전체 그림을 이해하는 데는 몰라도 지장 없어. 나중에 팀 프로젝트에서 데이터셋을 공유해야 할 때 찾아보면 되는 수준으로 취급해도 괜찮아.

## 실무 사용 여부

| 항목 | 실무 사용 |
|---|---|
| RAGAS 합성 데이터셋 생성 | **매우 자주 씀**. 수작업 QA셋 제작 비용을 줄이는 표준적 방법 |
| 생성된 데이터셋 품질 검수 | 자주 함 (다만 이 노트북처럼 별도 단계로 명시하기보다, 생성 후 샘플링해서 사람이 훑어보는 정도로 약식으로 처리하는 경우도 많음) |
| 원격 데이터셋 관리 | 팀/조직 규모에 따라 다름. 개인 프로젝트/해커톤 규모에서는 생략해도 무방 |
